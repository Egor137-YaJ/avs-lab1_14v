#### Теория: что такое Docker и Dev Container

**Зачем это нужно.** Лабу надо делать в Linux (Debian), а у тебя Mac. Можно было бы поставить виртуальную машину, но это тяжело. Docker даёт лёгкое изолированное окружение: «маленький Debian», который запускается за секунды и никак не мешает твоей системе.

**Образ и контейнер.** Аналогия с Python, которую тебе будет легко запомнить:

- **Образ (image)** — это как *класс*: неизменяемый шаблон («Debian + git + базовые утилиты»). Его скачивают один раз.
- **Контейнер (container)** — это как *объект* класса: запущенный экземпляр образа. У него своя файловая система, процессы и пользователи. Из одного образа можно создать сколько угодно контейнеров.

**Почему на Mac всё чуть сложнее.** Контейнеры не эмулируют целый компьютер, они пользуются ядром хостовой ОС. Но им нужно именно **Linux-ядро**, а у macOS ядро другое. Поэтому Docker Desktop на Mac тихо поднимает маленькую Linux-виртуалку, и все контейнеры работают внутри неё. Именно поэтому Docker Desktop должен быть запущен: без него этой виртуалки нет.

**Dev Container.** Это идея VS Code: окно редактора открыто на Mac, а всё остальное работает внутри контейнера — терминал, файлы, git. VS Code ставит в контейнер свой небольшой сервер и общается с ним. Поэтому в терминале VS Code ты окажешься в Debian, а не в macOS. Настройки контейнера (какой образ, какие расширения) хранятся в файле `.devcontainer/devcontainer.json`.

#### 2. Что такое `less` и зачем он нужен

##### Проблема, которую решает `less`

Любая команда в терминале выводит текст в **стандартный вывод (stdout)**, и терминал его просто печатает. Если вывод короткий, всё в порядке. Но некоторые команды выводят сотни строк. Например, `ls -lR ~/lab0` (рекурсивный список всех файлов) или справка `man ls`. Тогда текст пролетает мимо, и на экране остаются только последние строки. Начало потерялось.

Посмотрим на инструменты из твоего списка:

- **`cat`** вываливает весь файл сразу. Длинный файл тоже «пролетит».
- **`head` / `tail`** показывают только начало или только конец. Середину ты не увидишь.
- **`less`** открывает текст в **просмотрщике**. Ты видишь один экран и сам листаешь вперёд и назад, ищешь слова, ничего не теряешь.

Такие программы называются **пейджеры** (pager, от «page» — страница). Они показывают текст постранично.

##### Почему он называется «less»

Раньше в Unix был пейджер `more` («ещё»). Он умел листать только вперёд. Потом написали улучшенную версию, которая умеет листать и назад, и назвали её `less` в шутку: *«less is more»* — «меньше значит больше».

##### Как пользоваться

Есть два способа открыть текст:

1. **Файл:** `less имя_файла`
2. **Вывод другой команды через конвейер (pipe):** `ls -lR ~ | less`

Символ `|` — это **конвейер**. Он забирает stdout левой команды и подаёт его на вход правой. Поэтому `less` получает не файл, а поток текста от `ls`. Конвейеры тебе очень понадобятся в части 4 варианта, так что запомни идею: вывод одной команды становится входом другой.

Клавиши внутри `less`:

| Клавиша | Что делает |
|---|---|
| `Пробел` / `f` | на страницу вперёд |
| `b` | на страницу назад |
| `↓` `↑` или `j` `k` | на строку вниз / вверх |
| `g` / `G` | в начало / в конец |
| `/слово` + Enter | поиск вниз |
| `?слово` + Enter | поиск вверх |
| `n` / `N` | следующее / предыдущее совпадение |
| `q` | **выход** (самое важное) |

##### Зачем его ставили именно сейчас

1. **`man` показывает справку через `less`.** В README сказано: «по каждой команде можно получить справку `man [КОМАНДА]`». Сама страница справки выводится как раз через пейджер. В минимальном образе `less` вырезан, чтобы образ был меньше. Без пейджера справку читать неудобно.
2. **`git log` тоже использует `less`.** Когда коммитов станет много, git сам откроет историю в `less`. Если увидишь в терминале `:` или `(END)` и «зависание», это не ошибка: ты внутри `less`, нажми `q`.
3. **Тренировка из README.** Команда установки `less` показывает общий приём: так можно поставить любую недостающую утилиту.

Если `man ls` ответит `command not found`, значит, в образе нет и самого `man`. Тогда поставь его так же: `sudo apt-get install -y man-db`.

##### Важно для твоих скриптов

`less` **интерактивный**: он ждёт, пока ты нажмёшь `q`. Если вставить его в shell-скрипт, скрипт остановится и будет ждать тебя. Поэтому в скриптах выводи результат через `cat`, `head` и т.п., а `less` используй только руками, чтобы что-то посмотреть.

📸 **Скриншот:** открой `man ls` (справка отобразится в `less`) и сделай скриншот. Он покажет, что `less` установлен и работает. Выйди по `q`.

#### 3. Git: клонировать или нет

**Клонировать не нужно.** По заданию первая команда — `git init`, то есть репозиторий создаётся *локально*, а потом публикуется на GitHub. Если склонировать, `git init` уже будет не нужен, и шаг 1 части 1 выпадет из отчёта. Порядок такой: пустой репозиторий на GitHub → `git init` локально → связать их → `push`.

##### Немного теории git

- **Репозиторий** — это папка, за изменениями в которой следит git. Вся история хранится в скрытой подпапке `.git`, её и создаёт `git init`.
- У файла есть три состояния:
  1. **Рабочая папка (working tree):** ты изменил файл, git видит изменения, но пока ничего не делает. В `git status` такие файлы красные.
  2. **Индекс (staging area):** `git add` кладёт изменения «в корзину» для следующего снимка. В `git status` они зелёные.
  3. **Коммит:** `git commit -m "сообщение"` делает снимок всего, что лежит в индексе, и записывает его в историю. У коммита есть автор, дата и сообщение.
- **Удалённый репозиторий (remote)** — копия на GitHub. `git push` отправляет туда твои локальные коммиты.
- `git log` показывает историю коммитов, а `git status` — что сейчас изменено и что в индексе.

##### Где будет репозиторий — важный нюанс

Есть два места:

- `~/lab0` — дерево из варианта;

**Рекомендую так:**

- репозиторий = `~/lab0` (там и делается `git init`);

Хорошо, что ты подумал об этом заранее: для твоего варианта это действительно важно. Сначала теория, потом настройка.

#### Теория: кодировка и локаль

**Кодировка** — это правило, как буквы превращаются в байты. В UTF-8 латинская буква занимает 1 байт, а русская — 2 байта. Например, `Б` хранится как два байта `D0 91`.

**Локаль (locale)** — это настройка, которая говорит программам: «вот язык и кодировка пользователя». Из неё программы узнают:

- сколько байт составляют одну букву;
- какая буква заглавная, а какая строчная (`Б` ↔ `б`);
- в каком порядке сортировать буквы.

Локаль задаётся переменными окружения: `LANG` и группой `LC_*`, например `LC_CTYPE` (типы символов) и `LC_COLLATE` (порядок сортировки). Самая сильная из них — `LC_ALL`: она перекрывает все остальные.

**Почему это важно для твоей лабы.** В минимальном контейнере локаль обычно `POSIX` (она же `C`). В ней программа считает, что любой байт — отдельный символ, и ничего не знает о русских буквах. Последствия:

- **`grep -i`** (поиск без учёта регистра) не поймёт, что `Баринов` и `баринов` — одно и то же. В задании 4.2 нужно найти `баринов` «в любом регистре», а в файлах слово написано с заглавной. Без локали grep найдёт не всё, и ответ будет неверным.
- **`sort`** будет сортировать по байтам, а не по алфавиту. Например, `ё` окажется после `я`, а все заглавные буквы встанут раньше всех строчных. Это касается заданий 4.2, 4.4 и 4.5.

При этом `echo` и `cat` покажут русский текст нормально и без локали: они просто передают байты в терминал, а терминал Мака сам понимает UTF-8. Поэтому проблема коварная: на вид всё в порядке, а поиск и сортировка ошибаются.

#### Практика

##### 1. Посмотри, что сейчас

```
locale
locale -a
echo "Баринов" | grep -i "баринов"
```

- `locale` показывает текущие настройки. Скорее всего, там будет `POSIX` или пустые значения.
- `locale -a` показывает список установленных локалей. Скорее всего, только `C`, `C.utf8` и `POSIX`, русской нет.
- Последняя команда — тест. Если она ничего не вывела, grep не понимает регистр русских букв.

📸 **Скриншот** этих трёх команд «до». В отчёте это хорошо смотрится: видна проблема.

##### 2. Установи русскую локаль

```
sudo apt-get install -y locales
echo "ru_RU.UTF-8 UTF-8" | sudo tee -a /etc/locale.gen
sudo locale-gen
```

Что здесь происходит:

- **`locales`** — пакет с данными о языках. В минимальном образе его нет.
- **`/etc/locale.gen`** — список локалей, которые нужно собрать. Мы дописываем туда русскую.
- **`locale-gen`** собирает локали из этого списка.

**Почему `| sudo tee -a`, а не `sudo echo ... >> файл`?** Это напрямую связано с перенаправлениями из твоей лабы. В записи `sudo echo "..." >> /etc/locale.gen` знак `>>` обрабатывает *твоя* оболочка, ещё до запуска `sudo`. Она работает от `vscode`, и в системный файл ей писать нельзя, поэтому будет `Permission denied`. `sudo` в такой записи действует только на `echo`, которому права не нужны. Команда `tee -a` сама открывает файл и дописывает в него то, что пришло по конвейеру. Под `sudo` она работает от root, поэтому запись проходит.

##### 3. Включи локаль

Для текущего терминала:

```
export LANG=ru_RU.UTF-8
```

`export` задаёт переменную окружения, и все команды, запущенные из этого терминала, её увидят. Но действует она только до закрытия терминала.

Чтобы локаль включалась в каждом новом терминале, допиши эту строку в `~/.bashrc`. Это файл, который bash выполняет при каждом запуске:

```
echo 'export LANG=ru_RU.UTF-8' >> ~/.bashrc
```

Здесь `sudo` не нужен: `.bashrc` лежит в твоём домашнем каталоге. Одинарные кавычки нужны, чтобы строка записалась в файл как есть.

Открой новый терминал (кнопка `+` в панели терминала) и повтори проверку:

```

echo "Баринов" | grep -i "баринов"
```

Теперь `locale` должна показывать `ru_RU.UTF-8`, а grep — вывести `Баринов`.

📸 **Скриншот «после».** Вместе со скриншотом «до» он показывает, зачем понадобилась настройка.

Скрипт наследует переменные окружения из терминала, который его запустил, так что работать он будет. Но надёжнее явно задать локаль в начале скрипта части 3: `export LC_ALL=ru_RU.UTF-8`. #### `echo` на практике

**Что делает:** печатает свои аргументы в стандартный вывод (stdout) и добавляет в конце перевод строки. Больше ничего, это самая простая команда.

```
echo Привет мир
```

выведет `Привет мир`.

**Зачем кавычки.** Оболочка делит строку на слова по пробелам. Кавычки склеивают текст в один аргумент и защищают специальные символы. Разница между видами кавычек:

- **двойные `"..."`** — внутри подставляются переменные: `echo "$HOME"` выведет `/home/vscode`;
- **одинарные `'...'`** — всё берётся буквально: `echo '$HOME'` выведет `$HOME`.

Поэтому в `.bashrc` мы записывали строку в одинарных кавычках: нужно было, чтобы в файл попал сам текст `export LANG=...`.

**Куда уходит вывод.** По умолчанию на экран. Но его можно перенаправить, и именно так в лабе создаётся содержимое файлов:

- `echo "текст" > файл` — записать в файл, **затерев** старое содержимое;
- `echo "текст" >> файл` — **дописать** в конец файла;
- `echo "текст" | команда` — передать текст на вход другой команде (конвейер).

Как записать в файл три строки (например, для `barinov_plan`), подумай сам. Подсказка: либо несколько `echo` с `>>`, либо одна команда и `man bash`, раздел про `echo` и флаг `-e`. Это уже часть твоего скрипта.

#### `grep` и `grep -i` на практике

**Что делает:** читает текст построчно и выводит только те строки, в которых есть заданное сочетание (шаблон). Остальные строки отбрасывает. По сути это фильтр.

Текст `grep` может брать из двух мест:

- из файла: `grep "кухн" имя_файла`;
- из конвейера, если файл не указан: `команда | grep "кухн"`.

**Флаг `-i`** (*ignore case*) отключает учёт регистра: `Кухня`, `кухня` и `КУХНЯ` считаются совпадением.

**Разберём твой тест по шагам:**

1. `echo "Баринов"` выдаёт строку `Баринов`.
2. `|` передаёт её не на экран, а на вход `grep`.
3. `grep -i "баринов"` сравнивает строку с шаблоном без учёта регистра. Если совпало, печатает строку. Если нет, печатает **ничего**.

**Почему без локали совпадения нет.** В UTF-8 буква `Б` — это байты `D0 91`, а `б` — байты `D0 B1`. В локали `POSIX` grep не знает, что это буквы, и тем более не знает, что они пара «заглавная — строчная». Он видит просто разные байты, поэтому совпадения нет и вывод пустой. С `ru_RU.UTF-8` grep понимает, что `D0 91` — это `Б`, а её строчная пара — `б`, и находит строку. Пустой вывод на S06 и найденная строка на S08 и есть доказательство, что настройка сработала.

В части 4 понадобятся и другие флаги grep: исключение строк, рекурсивный поиск, вывод без имён файлов, подсчёт файлов. Разберём их, когда дойдём до заданий, по `man grep`.

#### Теория к следующему блоку: права доступа

##### Кто и что

У каждого файла и каталога есть три группы прав:

- **u** (user) — владелец, то есть ты, `vscode`;
- **g** (group) — группа владельца;
- **o** (others) — все остальные.

Для каждой группы есть три права:

| Право | Для файла | Для каталога |
|---|---|---|
| **r** (read) | читать содержимое | видеть список файлов внутри (`ls`) |
| **w** (write) | изменять содержимое | создавать, удалять и переименовывать файлы внутри |
| **x** (execute) | запускать как программу | **входить** в каталог (`cd`) и обращаться к файлам внутри |

Запись `rwxr-x---` — это три тройки подряд: владелец `rwx`, группа `r-x`, остальные `---`. Прочерк означает «права нет».

##### Числовой способ

Каждое право — это вес: **r = 4, w = 2, x = 1**. Для каждой тройки веса складываются в одну цифру:

- `rwx` = 4+2+1 = **7**
- `r-x` = 4+0+1 = **5**
- `rw-` = 4+2+0 = **6**
- `r--` = **4**
- `---` = **0**

Получается трёхзначное число в восьмеричной системе: первая цифра для владельца, вторая для группы, третья для остальных. Пример: `chmod 640 файл` означает `rw-r-----`.

##### Символьный способ

Здесь права задаются буквами: `кому` + `операция` + `какие права`. Операций три:

- **`=`** — установить ровно эти права, остальные убрать;
- **`+`** — добавить права;
- **`-`** — убрать права.

Несколько групп перечисляются через запятую **без пробелов**. Пустая часть после `=` значит «никаких прав».

Пример не из твоего варианта: `rwx--x--x` в символьном виде — это `chmod u=rwx,g=x,o= ...`. Нет, точнее `o=x`, потому что у остальных тоже `--x`. А `rw-------` записывается как `u=rw,g=,o=`.

Для лабы удобнее всего форма с `=`: она задаёт права полностью и однозначно, независимо от того, какие права были до этого.

##### Что из варианта каким способом делать

Задание прямо говорит: если права записаны числом — ставь числом, если буквами или словами — ставь символьно. Даже если `rwxr-x---` — это то же самое, что `750`, для `kitchen` нужно использовать символьный способ, иначе задание формально не выполнено.

Пройдись по списку из варианта и для каждой строки определи способ. Словесные описания («владелец — чтение и запись; группа — чтение; остальные — нет прав») сначала переведи в буквы, а потом запиши символьно.

##### Важен ли порядок установки прав

В общем случае важен. Если сначала отнять у каталога право `x` для владельца, ты больше не сможешь обратиться к файлам внутри, и следующие `chmod` для этих файлов упадут с `Permission denied`. Поэтому обычно сначала ставят права на файлы, а потом на каталоги.

Порядок по заданию: **status → add → commit → push**. Вот что делает каждая команда и на что обратить внимание.

**`git status`** (до add) показывает текущее состояние. Все файлы будут в разделе *Untracked files*, красным. Именно этот вывод нужен для скриншота 13.

**`git push -u origin main`** отправляет ветку `main` в `origin`. Флаг `-u` запоминает эту связь, и в частях 2 и 3 хватит просто `git push`.

#### Часть 2: теория перед скриптом

##### Как файл устроен внутри: inode

В Linux имя файла и сам файл — разные вещи:

- **inode** — это «карточка» файла на диске: размер, права, владелец, где лежат данные;
- **имя** в каталоге — просто запись «имя → номер inode».

Номер inode показывает `ls -i`. Попробуй, он пригодится для понимания.

##### Жёсткая ссылка (`ln` без флагов)

Это **ещё одно имя для того же inode**. Копии не создаётся, есть один файл с двумя именами:

- изменишь содержимое через одно имя — оно изменится и через другое;
- счётчик ссылок (второй столбец в `ls -l`) станет `2`;
- удалишь одно имя — файл продолжит жить под вторым. Данные удаляются, только когда счётчик доходит до 0.

Это прямо пригодится в задании 4.6: «файлы, у которых количество жёстких ссылок равно двум».

##### Символическая ссылка (`ln -s`)

Это **отдельный маленький файл, внутри которого записан путь** к цели, как ярлык. В `ls -l` она выглядит как `l...  имя -> куда_указывает`.

Главная ловушка: путь внутри симлинка хранится **как текст** и разрешается **относительно каталога, где лежит сама ссылка**, а не относительно того места, откуда ты запускал `ln`. И `ln -s` при создании **не проверяет**, существует ли цель. Если ошибёшься, получишь «битую» ссылку, которая выделяется в `ls` красным.

Применительно к твоим пунктам:

- **3.3:** ссылка `victor_menu` лежит в корне `lab0`, значит путь к цели считается от `lab0`;
- **3.4:** ссылка `hall_access` лежит в `victor/reception`, а цель — `../hall`. От `victor/reception` подъём на уровень вверх даёт `victor`, затем `hall`. Получается `victor/hall`, всё верно. Это и есть «относительная» ссылка: в неё записан именно текст `../hall`.

##### `cp` и `cp -r`

- `cp файл новое_место/новое_имя` — обычная копия: новый inode, независимый файл.
- Каталог копируется только рекурсивно: флаг `-r`.

Ловушка с `cp -r`: если каталога назначения **ещё нет**, копия создастся под этим именем. Если он **уже есть**, копия окажется **внутри** него, например `claude_backup/claude_monet/...`. В первом запуске каталога ещё нет, так что всё будет правильно.

##### `cat` и перенаправления

- `cat файл1 файл2` выводит файлы подряд, один за другим. Отсюда и название: con**cat**enate, «склеить».
- `> файл` направляет этот вывод в файл, создавая или затирая его. Это пункт 3.6.
- `>> файл` дописывает в конец. Это пункт 3.7. Если перепутать с `>`, содержимое `vika_schedule` пропадёт.

##### `mv`

`mv` перемещает или переименовывает. Внутри одной файловой системы данные никуда не копируются: меняется только запись «имя → inode» в каталогах. Поэтому `mv` работает мгновенно, а inode у файла остаётся тем же.

#### 1. `cat`

##### Что делает

`cat` берёт содержимое файлов и **выводит его как поток текста**. Сама по себе это очень простая команда: «прочитай файл и выдай всё, что в нём есть». Ничего не меняет, ничего не фильтрует.

Название — от *concatenate*, «склеивать цепочкой». Если дать ей несколько файлов, она выдаст их один за другим, как будто это один длинный файл.

##### Куда уходит вывод

Вот ключ к пониманию. Сам `cat` не знает, куда пойдёт текст: он просто «выливает» его в стандартный вывод. А куда этот вывод направить, решаешь ты:

| Запись | Что происходит |
|---|---|
| `cat файл` | на экран: так быстро смотрят небольшой файл |
| `cat а б` | на экран: сначала `а`, сразу за ним `б` |
| `cat а б > в` | склеенный текст уходит в файл `в`, который создаётся или **затирается** |
| `cat а >> в` | содержимое `а` **дописывается** в конец `в` |
| `cat а \| grep слово` | текст уходит на вход другой команде |

Представь `cat` как кран, а `>`, `>>` и `|` как шланги, которые ты к нему прикручиваешь. Важная тонкость: **файлы создаёт и записывает не `cat`, а оболочка**, когда видит `>` или `>>`. `cat` только выдаёт текст.

Отсюда коварная ловушка: `cat файл > файл` **опустошит файл**. Оболочка сначала открывает `файл` на запись и обнуляет его, а уже потом запускается `cat`, которому читать нечего.

Если запустить `cat` вообще без файлов, она читает то, что ты печатаешь с клавиатуры, и повторяет это. Выход — `Ctrl+D` («конец ввода»).

##### Где это у тебя в лабе

- **Часть 2, пункт 6** — склеить два файла в новый: `cat`, два файла и `>`.
- **Часть 2, пункт 7** — дописать один файл в конец другого: `cat` и `>>`.
- **Часть 4** — `cat` будет «источником» текста, который через `|` уходит в `grep`, `sort`, `wc`.
- **Скриншоты** — посмотреть, что лежит в файле.

#### 2. Нужен ли `#!/bin/bash`?

**Да, оставляй его первой строкой в каждом скрипте.**

Эта строка называется **shebang**: от `#` (sharp) и `!` (bang). Когда ты запускаешь файл как программу (`./part1.sh`), система смотрит на первые два символа. Если там `#!`, она читает остаток строки и понимает: «этот файл нужно выполнить программой `/bin/bash`». То есть `./part1.sh` на самом деле превращается в `/bin/bash ./part1.sh`.

Почему без неё «вроде тоже работало бы»:

- если запускать из bash, он при неудаче сам попробует выполнить файл как скрипт оболочки, и всё случайно сработает;
- но если скрипт запустит другая программа или другая оболочка, файл может выполниться не тем интерпретатором. Например, в Debian `/bin/sh` — это урезанная оболочка `dash`, и часть bash-синтаксиса в ней ломается.

Shebang делает запуск однозначным и сразу сообщает читающему, на каком языке написан файл.

Для самого bash эта строка обычная: `#` в bash начинает комментарий, поэтому при выполнении он её просто пропускает.

Если запускать скрипт явно, как `bash part1.sh`, shebang не используется: ты сам указал интерпретатор. Но преподаватель скорее всего будет запускать так же, как ты, через `./`.

#### 3. Ссылки: жёсткие и символические

##### Сначала: как устроен файл

Представь библиотеку:

- **Книга** на полке — это сами данные файла на диске. Вместе с карточкой, где записаны размер, права и владелец, это называется **inode**.
- **Запись в каталоге (картотеке)** — это **имя файла**. В ней написано только «название → номер полки, где стоит книга».

Когда ты видишь в папке файл `max_dish`, это запись в картотеке, которая указывает на книгу. Имя и данные — **разные вещи**. На этом построены оба вида ссылок.

##### Жёсткая ссылка: второе название той же книги

`ln исходный новое_имя` добавляет в картотеку **ещё одну запись**, которая указывает **на ту же самую книгу**.

- Копии **нет**: книга одна, просто у неё теперь два названия.
- Допишешь что-то через одно имя — это сразу видно и через другое, ведь книга одна и та же.
- Библиотека помнит, сколько записей ведёт к книге. Это **счётчик ссылок**, второй столбец в `ls -l`. Было `1`, стало `2`.
- Удалишь одно имя — книга останется, потому что на неё ещё ссылается другая запись. Книга выбрасывается, только когда счётчик дошёл до 0.
- Оба имени **равноправны**: нельзя сказать, какое из них «оригинал».

Ограничения: жёсткую ссылку нельзя сделать на каталог, и она не может вести на другой диск (номер полки имеет смысл только в своей библиотеке).

##### Символическая ссылка: записка «книга лежит там-то»

`ln -s цель имя_ссылки` создаёт **отдельный маленький файл-записку**, в которой написан **путь** к цели. Это то же самое, что «ярлык» в Windows или «псевдоним» на Маке.

- Это **самостоятельный файл** со своим inode. В `ls -l` он выглядит как `lrwxrwxrwx ... имя -> куда_указывает`. Буква `l` означает link.
- Когда ты открываешь ссылку, система читает записку и идёт по указанному пути.
- Удалишь или переместишь цель — записка останется, но будет вести в пустоту. Это **битая ссылка**, `ls` выделяет её красным.
- Счётчик ссылок цели **не меняется**: записка не является ещё одним именем книги.
- Может указывать на каталог и на другой диск: это ведь просто текст с путём.

**Самое важное для твоего варианта.** Путь в записке — это **текст**, и читается он **с того места, где лежит сама записка**. Записка `hall_access`, лежащая в `victor/reception`, с текстом `../hall` означает: «из `reception` подняться на уровень вверх (в `victor`), там зайти в `hall`». Неважно, из какого каталога ты запускал команду `ln`.

##### Сравнение

| | Жёсткая (`ln`) | Символическая (`ln -s`) |
|---|---|---|
| Что это | ещё одно имя того же файла | отдельный файл с путём внутри |
| inode | тот же, что у оригинала | свой |
| В `ls -l` | обычный файл `-`, счётчик растёт | `l`, видно `-> цель` |
| Удалили оригинал | данные живы, доступны по второму имени | ссылка становится битой |
| На каталог | нельзя | можно |
| На другой диск | нельзя | можно |

##### Где это встречается в реальной жизни

**Символические ссылки встречаются повсюду:**

- **Версии программ.** `python3` в системе — обычно ссылка на конкретную версию вроде `python3.13`. Обновили Python — переставили ссылку, и все программы автоматически используют новую версию.
- **Прямо в твоём контейнере.** Введи `ls -ld /bin`. Скорее всего увидишь `/bin -> usr/bin`: в современном Debian вся папка `/bin` — это ссылка.
- **Конфиги.** Многие хранят настройки (`.bashrc` и т.п.) в одном git-репозитории, а в домашнюю папку кладут симлинки на них.
- **Деплой сайтов.** Есть ссылка `current -> releases/v42`. Выкатили новую версию — переставили ссылку, и откатиться назад можно за секунду.

**Жёсткие ссылки встречаются реже, но тоже работают:**

- **Резервные копии.** Time Machine на Маке и утилиты вроде `rsync` делают «снимки» каждый день. Неизменившиеся файлы не копируются заново, а связываются жёсткими ссылками со вчерашними: место на диске не тратится, а каждый снимок выглядит полным.
- **Сама файловая система.** `.` и `..` в каждом каталоге — это жёсткие ссылки. Поэтому у `victor` на скриншоте 11 счётчик был `7`: имя `victor` в `lab0`, `.` внутри самого `victor` и `..` в каждом из пяти подкаталогов.

##### Конвейер: главная идея

Каждое задание части 4 — это **цепочка фильтров через `|`**. Первая команда выдаёт «сырой» текст, а каждая следующая что-то с ним делает и передаёт дальше. Хороший способ составлять такие команды — **читать задание по фразам**: каждая фраза обычно соответствует одному звену цепочки. Собирать цепочку тоже удобнее по одному звену: добавил звено, посмотрел вывод, добавил следующее.

##### `grep` — оставить или выкинуть строки

| Флаг | Что делает |
|---|---|
| `grep 'шаблон'` | оставить строки, где есть шаблон |
| `-v` | наоборот: **выкинуть** строки с шаблоном |
| `-i` | не учитывать регистр |
| `-e A -e B` | несколько шаблонов, совпадение с любым («A или B») |
| `-r` | искать рекурсивно во всех файлах каталога |
| `-h` | не печатать имена файлов перед найденными строками |
| `-l` | вывести только **имена файлов**, где есть совпадение |
| `-c` | количество совпавших **строк** в каждом файле |

Шаблон в `grep` — это **регулярное выражение**. Два символа понадобятся тебе прямо сейчас:

- `^` означает «начало строки». `'^-'` — строка, которая **начинается** с минуса;
- `$` означает «конец строки».

Шаблоны бери в одинарные кавычки, чтобы оболочка не трогала спецсимволы.

##### `sort` — упорядочить строки

| Флаг | Что делает |
|---|---|
| `sort` | по алфавиту, по всей строке |
| `-r` | в обратном порядке |
| `-n` | сравнивать **как числа** |
| `-k N` | сортировать по N-му полю (столбцу); поля разделяются пробелами |

Почему важен `-n`: без него `sort` сравнивает текст посимвольно, и `"99"` окажется **больше** `"426"`, потому что символ `9` больше символа `4`. С `-n` сравниваются значения чисел.

Про `-k`: запись `-k5` означает «начиная с 5-го поля и до конца строки». Чтобы сортировать **только** по 5-му полю, пишут `-k5,5`. Подробности есть в `man sort`, раздел про KEYDEF.

##### `head` / `tail` — взять начало или конец

`head -n 5` оставляет первые 5 строк, `tail -n 1` — последнюю.

##### `wc` — посчитать

`wc -l` считает строки, `wc -w` — слова, `wc -c` — байты.

##### Маски (globbing)

Это **не регулярные выражения**. Маски разворачивает **оболочка**, ещё до запуска команды:

- `*` — любая последовательность символов, в том числе пустая;
- `?` — ровно один любой символ.

Например, `guest_*` превратится в список подходящих имён файлов, и команда получит уже готовые имена. Понадобится в задании 4.4.

| | Где работает | Спецсимволы |

| `-l` | вывести только **имена файлов**, где есть совпадение (каждый один раз) |
| `-c` | количество совпавших **строк** в каждом файле, включая файлы с нулём |

Спецсимволы **регулярных выражений**: они работают только внутри шаблона `grep '...'`:

- `^` — начало строки (`'^-'` — строка начинается с минуса);
- `$` — конец строки.

Шаблоны бери в одинарные кавычки.

#### `sort`: упорядочить строки

| Флаг | Что делает |
|---|---|
| `sort` | по алфавиту, по всей строке |
| `-r` | в обратном порядке |
| `-n` | сравнивать **как числа** (иначе `"99"` > `"426"`) |
| `-k N,N` | сортировать только по N-му полю (столбцу) |
| `-u` | убрать повторяющиеся строки (тебе не нужен) |

#### `head` / `tail`: начало или конец

| Запись | Что делает |
|---|---|
| `head -n 5` | первые 5 строк |
| `tail -n 1` | последняя строка |
| без `-n` | по умолчанию 10 строк |
| `-q` | не печатать заголовки `==> файл <==`, когда файлов несколько |

Два режима работы: с **именем файла** команда читает файл, а **без имени, после `|`**, берёт поток от предыдущей команды.

#### `wc`: посчитать

| Флаг | Что считает |
|---|---|
| `-l` | строки |
| `-w` | слова |
| `-c` | байты |

#### Маски: разворачивает оболочка, в путях к файлам

| Символ | Значение |
|---|---|
| `*` | любое количество любых символов, в том числе ноль |
| `?` | ровно один любой символ |

Проверить, во что развернётся маска: `echo путь/маска`.

Маска и регулярное выражение — **разные языки**: `^` в пути к файлу не работает, а `*` в `grep` означает совсем другое.

#### Как устроен конвейер

- **Слева — источник**: читает файлы и выдаёт текст (`cat`, `ls`, `grep -r`, `head`/`tail` с именами файлов).
- **Дальше — фильтры**: каждый берёт текст слева и отдаёт направо (`grep`, `sort`, `head` без файла, `wc`).
- `|` передаёт **данные**, а не аргументы.
- `{ команда1; команда2; }` объединяет вывод нескольких команд в один поток.
- Порядок звеньев обычно совпадает с порядком фраз в задании. Собирай по одному звену и проверяй вывод.

## 38. Егор

а напомни , что такое ln?

### Claude

`ln` (от *link*, «связь») создаёт **ссылку** на файл. Бывает два вида ссылок, и выбор между ними зависит от флага.

#### Аналогия с библиотекой

- **Книга на полке** — это данные файла вместе с карточкой (размер, права, владелец). Это называется **inode**.
- **Запись в картотеке** — это **имя файла**, оно просто указывает на книгу.

#### Жёсткая ссылка: `ln цель новое_имя`

Это **ещё одна запись в картотеке на ту же самую книгу**.

- Копии нет: файл один, просто у него два имени.
- Изменения через одно имя видны через другое.
- **Счётчик ссылок** (второй столбец в `ls -l`) становится `2`.
- Удалишь одно имя — данные останутся под другим.
- Нельзя сделать на каталог или на другой диск.

У тебя это `guest_list` и `guest_list_copy`: оба со счётчиком `2`.

#### Символическая ссылка: `ln -s цель имя_ссылки`

Это **отдельная записка, на которой написан путь** к цели, как ярлык в Windows.

- Это самостоятельный файл, свой inode.
- В `ls -l` строка начинается с `l`, в конце видно `имя -> цель`.
- Удалишь цель — записка станет **битой** (в `ls` она красная).
- Счётчик ссылок цели не меняется.
- Может указывать на каталог.
- **Путь в записке читается от того каталога, где лежит сама ссылка.**

У тебя это `victor_menu -> victor/kitchen/barinov_plan` и `hall_access -> ../hall`.

#### Сравнение

| | `ln` (жёсткая) | `ln -s` (символическая) |
|---|---|---|
| Что это | второе имя того же файла | файл-записка с путём |
| В `ls -l` | начинается с `-`, счётчик `2` | начинается с `l`, есть `->` |
| Удалили оригинал | данные живы | ссылка битая |

#### Как это пригодится в 4.6 и 4.7

- **4.6** «обычные файлы с двумя жёсткими ссылками»: в `ls -l` строка начинается с `-`, а во **втором столбце** стоит `2`.
- **4.7** «символические ссылки»: строки, которые **начинаются с `l`**.
